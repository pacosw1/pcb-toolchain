# ESP32-CORE rev B: single versus sprints (#1399)

**Both matched single runs qualify for the preregistered benchmark; neither sprint run does.** The additional one-CPU single also qualifies. Every qualifying single produces the same board. The unchanged full gate accepts none of these runs: the singles retain five stale RP-001 exemptions, and the sprints also have actual reference-plane failures. No CAD, rules, exemptions, router or gate implementation was changed for this study.

The no-go for adding LLM scheduling/ranking remains: this experiment supplies no supporting benefit. It tests the existing deterministic modes, not an LLM policy. Single mode has automatic reference-plane feedback that sprint mode lacks, and other work overlapped on the shared host. These results therefore do not isolate scheduler speedup, CPU scaling, or an LLM's potential benefit.

This closes the previously unmeasured large-board comparison in the [earlier benchmark](2026-11-05-sprint-benchmark.md), under the explicitly different source, memory and measured budget below. Historical results are not pooled with this sample.

## Interpretation and observed host activity

Single `run` applies automatic reference-plane feedback and reroutes; `sprint-finish` writes and checks a candidate without the same feedback loop. That asymmetry was preregistered. The sprint failures make the missing deterministic feedback path directly relevant; this study does not establish that scheduling itself caused the gap. Whole-job costs include each mode's unchanged behavior, not hypothetical acceptance after cleaning exemptions or adding feedback.

The host was shared from the outset. Other agents later recorded these approximate windows in task comments 5838 and 5839; their CPU cost was not separately measured:

| UTC window | Reported activity | Overlapping comparison |
|---|---|---|
| Nov 5 23:48-23:50 | PR70 cargo tests, two compiles, one 8-CPU / 8-GiB container | single-a end, sprint-a start |
| Nov 5 23:55-Nov 6 00:01 | Release Linux builds, sequential 2-CPU / 4-GiB containers | sprint-a |
| Nov 6 00:01-00:07 | Release smoke, 8 CPUs / 16 GiB, including an ENV-SENSE route | sprint-a, sprint-b |
| Nov 6 00:10:24-00:10:26 | Brief remote compression of completed calibration/single-a logs | sprint-b |
| Nov 6 00:11:57-00:11:59 | Brief remote compression of old #1389 logs | sprint-b |
| Nov 6 00:12:26-00:12:28 | Brief remote compression of completed sprint-a logs | sprint-b |
| Throughout, exact trace unavailable | Merge queue CI and other host work | shared-host limitation |

No active experiment inputs, harness, binary or driver were changed by this activity. It remains a possible timing confound; no zero-interference assumption, post-hoc correction, rerun or causal speedup claim is made. The one-CPU result is likewise not evidence that reducing CPUs improves performance. Two repetitions and one board do not establish general router quality or statistical significance.

**Decision:** keep the LLM scheduling/ranking no-go on the available evidence. Deterministic modes still differ in a known verification-feedback capability, and sprints provide no qualifying candidate here despite spending more operation CPU in these observations. This is not a test of an LLM policy or proof that one could never help. No new optimization or experiment is authorized by this report.
