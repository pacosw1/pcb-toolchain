# Crystals as a critical first stage (2026-11-06, branch codex/router-crystals)

## Change

Opt-in only. Policy `"crystals": "route"` -> `iotroute run --route-crystals` (needs `--lock-from`). Pairs stay locked. Nets with DRU
via_count 0 that are not pair members are stripped from the locked input and named in model `critical_nets`. Core `critical.rs`
routes them before every other net, against fixed copper only. It uses `route_net` with each net's own rules: width, clearance,
DRU pair rules, keepouts and via budget. A budget of 0 means one layer, the layer of the pads. Nets that share a footprint form one
group (crystal legs). Each order of a group is tried (all orders up to 4 nets). The stage keeps the fewest open nets, then the least
length + leg imbalance. Routed nets become fixed copper: the negotiation routes around them and never rips them up. A net the stage
cannot route keeps no copper and goes to the negotiation. Without the flag the model, args record and route are unchanged.

Caveat: the selector is "DRU via_count 0, not a pair member". On boards where that DRU rule covers non-crystal nets, those nets are
routed first too. Examples: CELLULAR RF class `disallow via`, POE-ETHERNET one-layer POE nets.

Tests: 3 core tests (tests_critical.rs), 1 lock, 1 run, 1 policy test; full `cargo test --release --locked` passes.

## Benchmark

Local Mac, route image `iot-lab-route:10.0-nightly-4fe1ca2060` under x86 emulation. Same iotroute build in both arms
(sha256 f0c05e77...). The only difference is the policy: `policies/lock.json` = `{"keep":"lock-nets","return_exempt":true}`, and
`policies/route.json` adds `"crystals":"route"`. Suite `router-crystals`, metric native, treatment router.

**Non-active boards.** The suite used FW-IO (development) and NET-CORE (holdout). Neither board is lifecycle "active". After the
coordinator's correction, the suite was stopped at a trial boundary after the 4 FW-IO trials. The first NET-CORE trial's container
was killed within about 5 s of starting, with no run sealed. There is no sealed `result.json` and no tool verdict. Raw trials
(`crystals-bench/out2/trials`, runs under `crystals-bench/.gate/cli`):

| Trial | Run | iotroute run | DRC / open / parity | Tracks / vias | Length mm | Core passes | Gate |
| --- | --- | --- | --- | --- | --- | --- | --- |
| FW-IO r1 lock | run-XA2sHw | PASS | 0 / 0 / 0 | 652 / 154 | 1258.3 | 10 | exit 0 |
| FW-IO r1 route | run-4Vg2tP | PASS | 0 / 0 / 0 | 653 / 154 | 1258.4 | 10 | exit 0 |
| FW-IO r2 lock | run-buuaxp | PASS | 0 / 0 / 0 | 652 / 154 | 1258.3 | 10 | exit 0 |
| FW-IO r2 route | run-vmbumV | PASS | 0 / 0 / 0 | 653 / 154 | 1258.4 | 10 | exit 0 |

Repeated runs gave byte-identical boards: the router has no route seed in the policy, so seeds repeat.

FW-IO crystal legs: hand copper HSE_IN 4.90 mm and HSE_OUT 2.46 mm on F.Cu. Routed: HSE_IN 4.98 mm and HSE_OUT 2.46 mm on F.Cu, no
via. The stage note reports an imbalance of 2.52 mm, which is set by the pad positions. The routed result is equivalent to the hand
copper. This is 1 board with n = 1 distinct outcome: no evidence of better or worse.

**Active boards.** None of the active boards (ENV-SENSE, FIELD-24V-BUS, BASE-PWR, BASE-PWR-B, BASE-PWR-C, CELLULAR-B) has a crystal
via_count 0 net. BASE-PWR* have via_count max 4 / max 1. CELLULAR-B's only via_count 0 nets are the RF class (`disallow via`,
D-120 coplanar line), which are not crystals. A development + holdout suite therefore cannot be formed on active boards, and
benchmarking stopped there.
